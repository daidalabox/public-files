結論:PHPを、8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 以上に更新し、PHP-FPMかWebサーバーを再起動してください。8.1以下は通常の公式リリースで修正版が提供されないため、OS・保守ベンダーのバックポート適用状況を確認し、可能ならサポート対象の系列へ移してください。更新までの間は外部公開を制限してください。

2026年10月21日、PHPの開発チームが緊急の修正版を出しました。対象は「PHP2Shell」と呼ばれる2件の脆弱性(CVE-2026-109618と109619)で、深刻度はどちらもCVSS v4.0で9.2です。ログインなしで、外からサーバー上のプログラムを動かされるおそれがあります。

アプリではなくPHPそのものの問題です。WordPressやLaravelを最新にしても、PHPを更新しなければ直りません。この記事は、サーバーを管理する技術者向けに、対象の見分け方と、今日やることをまとめたものです。

この記事でわかること

  • 対象かどうかは、PHPのバージョンと動かし方で決まる
  • 根本対策は「修正版に更新して、再起動」だけ
  • 更新できないものは外から隠し、侵入の跡を確かめる

自分の環境は対象か

各系列で、修正版より古いものはすべて対象です。修正版と同じか新しければ、今回の件は対策済みです。

確認は、サーバーで php -v を実行します。ただし、コマンドで見えるPHPと、Webで動いているPHPが別のことがあります。Webで動いている側は、phpinfo の表示か、WordPressなら管理画面の「サイトヘルス」で確かめてください。

8.1以下は、公式の通常の修正版が出ません。重大さを考えて、7.4・8.0・8.1向けに最小限の修正ソースが公開されましたが、実際には自分でビルドするか、OSやLTSベンダーのパッケージに頼ることになります。

動かし方で、危なさはどう変わるか

PHPの開発チームは、Apacheにmod_phpで組み込んだ構成を最も危ないとしています。アプリのコードが動く前に、認証のないリクエストで攻撃が成り立つことが実証されています。

PHP-FPM、php-cgi、LiteSpeed、FrankenPHPの構成も対象です。一方で、PHP-FPMでは1件目(109618)の完全な攻撃は示されていない、という見方もあります。Red HatはRHELの標準がPHP-FPMであることを理由に、深刻度を「Important」としています(CVSS v3で8.1。NVDは9.8)。

ただし、「FPMだから大丈夫」とは考えないでください。2件目(109619)は別の不具合で、FPMでも対象です。どちらの構成でも、更新が前提です。

今日やること:洗い出して、更新して、再起動する

1つ目は、PHPの入っている場所の洗い出しです。Webサーバーだけでなく、cPanelやPleskなどの管理パネル、ベンダー製の機器、Windowsのソフトに同梱されたPHPも対象になります。たとえばPalo Alto Networksは、自社のPAN-OSとPanoramaが影響を受けると公表しています。

2つ目は、修正版への更新と再起動です。パッケージを更新しただけでは、動いているプロセスは古いままです。PHP-FPMかWebサーバーを再起動し、もう一度Web側のバージョンを確かめてください。

OSのパッケージは、対応にばらつきがあります。10月22日早朝の時点で、Debian 12・13は修正済み、RHEL 9は一部のみ、RHEL 10とRocky Linuxは未修正、AlmaLinuxは修正版がテスト用リポジトリにある段階でした。自分のOSの最新のお知らせを確認してください。

レンタルサーバーなら、まず事業者のお知らせを見ます。国内の各社も、PHPの更新や緊急メンテナンスを進めています。8.1以下を選んでいる場合は、自分で8.2以降に切り替える必要があります。テーマやプラグインが古いと表示が崩れることがあるため、切り替えの前にバックアップを取ってください。

すぐ更新できないときは、どう時間を稼ぐか

完全な回避策はありません。PHPの開発チームも、安全な選択は更新だけとしています。そのうえで、更新までの間に攻撃の経路を減らす設定が示されています。

1件目(109618)向けの設定です。

  • memory_limit=-1 を、アプリから上書きできない形で設定する(メモリの上限はコンテナやcgroupで掛ける)
  • post_max_size を下げる(ファイルのアップロードがなければ8M、あれば32M)
  • Webサーバーやプロキシで、リクエストの大きさと数を制限する

2件目(109619)向けの設定です。

  • session.upload_progress.enabled=0 にして、すべてのワーカーを再起動する
  • PHP 8.5なら fatal_error_backtraces=0 にする

それでも足りないので、更新できないサーバーは、公開ネットワークから外すか、VPNやWAFの内側に置いてください。

侵入されていないかを、どう確かめるか

この攻撃は、アプリのコードが動く前に起きることがあります。アプリのログだけでは気づけないため、侵入した後の動きを見ます。

php-fpm、php-cgi、httpd、apache2 のプロセスから、シェル・スクリプトの実行環境・curlやwgetが起動していたら警戒してください。見つかったら、サーバーを切り離してログを保全し、次を調べます。

  • Webの公開フォルダに増えたファイル(Webシェル)
  • 新しいcronジョブやタスク
  • 見覚えのないアカウント

悪用はもう始まっているのか

情報が錯綜しています。10月21日の時点で、PHPの開発チームは実際の悪用を報告しておらず、米国のCISAも悪用済みの一覧に入れていません。一方で、AikidoやPatchstackは、実際の攻撃を確認したと述べています(詳細は未公開)。

今回は、予定されていた公表日(10月22日)の2日前に情報が漏れ、修正版は予定より1日早い21日に出ました。2024年にPHPのCGIモードで見つかった脆弱性では、公表から24時間以内に攻撃の試みが観測されました。「公式に悪用が確認されてから」では遅いと考えて、今日のうちに手を付けてください。

まとめ

  • 修正版は 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35。更新したら、必ず再起動してWeb側で確かめる
  • 8.1以下は通常の公式修正版がない。ベンダーのバックポートを確認し、サポート対象の系列へ移行。更新できなければ公開範囲を制限する
  • 設定での緩和は時間稼ぎ。PHPの処理から外部コマンドが動いていないかも見る

明日からの一歩

まずは、管理しているサーバーで php -v と、Web側のバージョン表示を並べて確かめてください。2つが違っていたら、そこが見落としやすい場所です。

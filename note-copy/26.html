# 手順5. あるべき姿を描く

# 実際にあった話：現場の運用に踏み込むのが一番重い

複数の拠点を持つある会社で、業務の記録のシステムが、請求のためにしか使われていない状態がありました。拠点ごとに入力のやり方がばらばらで、特に大きな拠点では、日報の書き方が他とまるで違っていました。

各拠点の担当者でチームを作り、日報の項目と書き方を統一することにしました。一番重かったのは、システムの設定ではなく、各拠点に根づいた現場の運用に踏み込むことでした。「うちはずっとこのやり方でやってきた」という声に、拠点ごとに向き合う必要があったからです。

ここで役に立ったのが、先に決めた原則でした。「入力は1回」「正しいデータは1か所」という原則があったので、「この拠点のやり方が悪い」ではなく、「会社全体の原則に合わせる」という話し方ができました。

# 何をするか

手順4で見えた根っこを解消した、「こうあるべき」という全体の設計図を描きます。第1回で書いた「全体を見て決める軸」を、ここで形にするのです。

# 先に「原則」を決める

いきなりシステムの構成を考えるのではなく、先に全体で守る原則を決めます。原則があると、後で迷ったときに判断できます。

原則の例です。組織に合わせて、5つ程度に絞ります。

  1. 入力は1回だけ:同じ情報を、2か所以上で入力しない
  2. 正しいデータは1か所:データごとに持ち主を決め、ほかはそこから受け取る
  3. 紙は入口で止める:紙で受け取ったものは、最初の段階でデータにする
  4. 例外は書き残す:決まった流れから外れる処理は、手順を文書にする
  5. 新しく入れる前に確かめる:新しいシステムは、この設計図に合うかを確かめてから決める

この原則は、手順10の「元に戻らない仕組み」の土台にもなります。

# 業務の流れを先に決める

システムから考えると、また部門ごとの最適に戻ってしまいます。必ず、業務の流れを先に決めます。

業務の流れを見直すときは、次の4つの順で考えると整理しやすくなります。業務改善でよく使われる考え方です。

  • 1(考え方:なくす、問いかけ:この作業は、そもそも必要か。やめたら誰が困るか)
  • 2(考え方:まとめる、問いかけ:別々にやっている作業を、1回にまとめられないか)
  • 3(考え方:入れ替える、問いかけ:順番や担当を変えると、楽にならないか)
  • 4(考え方:簡単にする、問いかけ:残った作業を、もっと簡単にできないか)

「なくす」から考えるのが大事です。システムで速くする前に、やらなくてよい作業をやめるほうが、効果が大きく、費用もかかりません。

第1回で書いた「やらなくてもよいはずの作業」は、ここで見つかります。理由を調べると、「前の担当者がやっていたから」「昔、一度問題があったから」というものが少なくありません。

# データの持ち主表を作る

データごとに、どのシステムを「正」とするかを決めます。

  • 社員の基本情報(氏名・所属・雇用の形)(持ち主(正とするシステム):人事のシステム、受け取る側:勤怠、給与、各部門のシステム、更新する人:人事の担当者)
  • 商品の情報(商品コード・単位・価格)(持ち主(正とするシステム):販売管理のシステム、受け取る側:在庫、会計、Webの受注、更新する人:商品の担当者)
  • 在庫の数(持ち主(正とするシステム):在庫(倉庫)のシステム、受け取る側:販売管理、会計、更新する人:倉庫の担当者)
  • 顧客の情報(持ち主(正とするシステム):販売管理など業務の中心となるシステム、受け取る側:請求、会計、更新する人:営業事務の担当者)
  • 請求の結果(持ち主(正とするシステム):請求のシステム、受け取る側:会計、更新する人:請求の担当者)

この表で一番大事なのは、「更新する人」の列です。持ち主のシステムを決めても、誰が更新するかが決まっていなければ、結局ほかの場所で直してしまいます。

# 残す・入れ替える・やめるを決める

システム台帳の1つ1つについて、次の基準で判断します。

  • 残す(当てはまる条件:設計図に合っている。または、合わせられる。費用が見合っている)
  • 設定や使い方を変える(当てはまる条件:システムは良いが、使い方や連携が原則に合っていない)
  • 入れ替える(当てはまる条件:設計図に合わせられない。保守が終わる。費用が見合わない)
  • やめる(当てはまる条件:使われていない。ほかのシステムで代わりができる)

入れ替えは、最後の手段と考えてください。入れ替えは費用も時間もかかり、現場の負担も大きいからです。第2回で書いたように、入れて間もないシステムは、無理に変えず、使い方と業務の流れで改善するほうが良いことが多くあります。

# 全体図を1枚にする

最後に、あるべき姿を1枚の図にします。手順2のデータの流れ図と同じ書き方で、点線の矢印(手作業)ができるだけ実線(自動)に変わった姿を描きます。

今の図とあるべき姿の図を並べると、何が変わるのかが一目で分かります。この2枚は、手順7の合意でそのまま使えます。

# 守るべき制約を書き添える

あるべき姿を描くときは、守らなければならない制約も書き添えます。

  • セキュリティのためにネットワークを分けている:顧客の個人情報や機密の情報を扱う部分と、事務の部分を分けている場合、何でも自由につなぐわけにはいきません。どのデータを、どの方向に、どんな方法で渡すかを決めます。
  • 制度で決まった書式・保存のルール:報告の書式や、記録の保存期間など、変えられないもの
  • 契約の期間:途中で解約すると違約金がかかるものなど

制約を先に書いておくと、「理想的だが実現できない設計図」になるのを防げます。

# AIで時間を減らす

  • 原則の叩き台:根っこの原因の一覧を渡し、「これを防ぐための全体の原則を5つ、短い言葉で」と頼みます。
  • 業務の流れの見直し:今の業務フローを文章で渡し、「なくす・まとめる・入れ替える・簡単にする、の順で改善案を出して」と頼むと、見落としていた案が出てきます。
  • 注意:AIの案は、現場の制約(制度・契約・セキュリティ)を知りません。必ず制約と照らし合わせます。

# つまずきやすい所

  • 製品のカタログから考え始める:製品を見ると、機能に目を奪われます。先に原則と業務の流れを決め、製品はそれに合うものを探します。
  • 完璧を目指す:点線の矢印をすべて消す必要はありません。手間の大きいものから消していけば十分です。
  • 現場を置き去りにする:あるべき姿を担当者だけで描くと、現場から「こんなの無理」と言われます。下書きの段階で、部門の責任者に見てもらいます。

# 手順6. 段階的な計画にする

# 実際にあった話:1店舗から始めた入れ替え

ある小売業で、店舗の無線の不具合が多発していました。全店の機器を一度に入れ替える案もありましたが、まず1店舗だけで先に入れ替え、本当に改善するかを確かめることにしました。

1店舗で効果がはっきり出たので、その結果を材料に全店への展開が決まりました。筆者がその組織を離れた後も、方針は引き継がれ、全店への展開は順調に終わったと聞いています。

最初の施策を小さくすると、失敗しても傷が浅く、成功すれば次の説得材料になります。 一度に全部を変えるより、結果的に早く終わることが多いのです。

# 何をするか

今の姿とあるべき姿の差を、いくつかの施策に分け、順番を決めます。一度に全部を変えるのではなく、段階的に進める計画にします。

# 施策カードを作る

施策ごとに、次の項目を1枚にまとめます。

  • 施策の名前(書く内容:例：社員の情報を人事のシステムに一本化する)
  • 解消する根っこ(書く内容:手順4のどの原因を解消するか)
  • 効果(書く内容:減る時間・コスト(手順3の数字から))
  • 費用(書く内容:初期の費用、毎月・毎年の費用、社内の手間)
  • 期間(書く内容:準備から定着までの目安)
  • 前提(書く内容:先に終わっていないといけない施策)
  • 関係する部門(書く内容:影響を受ける部門と人)
  • リスク(書く内容:うまくいかなかったときの影響)

# 点数を付けて比べる

施策カードがそろったら、点数を付けて比べます。これは複数部門で議論を始めるための簡易モデルであり、点数の合計を投資対効果と同一視しません。点数の付け方の例です。

  • 効果(3点:年間の削減が大きい、2点:中くらい、1点:小さい)
  • 緊急度(3点:期限が近い・止まると大きな影響、2点:1年以内に必要、1点:急がない)
  • 費用(3点:小さい、2点:中くらい、1点:大きい)
  • 難しさ(3点:1部門で済む・簡単、2点:2〜3部門、1点:全体に影響・難しい)

費用と難しさは、「小さい・簡単なほど点数が高い」ことに注意してください。合計の点数が高いものが、優先度の高い施策です。

ただし、点数だけで決めてはいけません。最後に前後の関係を確かめます。例えば、「倉庫の在庫を販売管理とつなぐ」は、「商品の情報を一本化する」が終わっていないと進められません。点数が高くても、前提が終わっていなければ後に回します。

# 最初の施策の選び方

最初の施策は、特に慎重に選びます。最初の成功が、その後のすべての施策を進めるときの説得材料になるからです。

最初の施策に向いている条件は、次の通りです。

  • 効果が目に見える(現場が「楽になった」と実感できる)
  • 3か月程度で結果が出る
  • 関係する部門が少ない
  • 失敗しても、元に戻せる

逆に、最初に一番大きく難しい施策を選ぶと、時間がかかり、途中で関係者の熱が冷めてしまいます。

# 段階に分けた計画表

施策を、3つの段階に分けて並べます。

  • 第1段階(期間の目安:半年以内、内容の例:効果が見えやすい施策。台帳と決まりづくり。使っていない契約の整理)
  • 第2段階(期間の目安:半年〜1年、内容の例:データの持ち主の一本化。主要なシステムのつなぎ込み)
  • 第3段階(期間の目安:1〜3年、内容の例:大きな入れ替え。保守の終了に合わせた更新)

第3段階の大きな入れ替えは、保守の終了や契約の更新の時期に合わせると、無駄な費用を抑えられます。①の手順2で作った台帳の「契約」の欄が、ここで役に立ちます。

# 製品の候補を絞る

この段階で、施策ごとに製品の候補を2〜3つに絞ります。最終決定は、業務を詳しく聞いた後(手順8)です。

候補を比べる観点です。

  • 機能(確かめること:あるべき姿の業務の流れに合うか。足りない機能は何か)
  • つながり(確かめること:ほかのシステムとデータをやり取りできるか。その費用はいくらか)
  • 費用(確かめること:初期の費用、毎月の費用、連携の追加費用、5年間の合計)
  • サポート(確かめること:問い合わせの窓口、対応の時間、導入時の支援)
  • 乗り換えやすさ(確かめること:やめるときに、データを取り出せるか。どんな形式か)
  • セキュリティ(確かめること:データの置き場所、アクセスの管理、記録の残り方)
  • 実績(確かめること:同じ業種・同じくらいの規模での導入例)

特に「つながり」と「乗り換えやすさ」は、第2回で書いたベンダー側の事情に直結します。連携が追加費用になる、データを取り出せない、という製品は、後で必ず問題になります。最初の段階で確かめておきます。

# 費用は5年で考える

費用は、初期の費用だけでなく、5年間の合計で考えます。5年は比較のための仮置きであり、契約期間や機器更新周期に応じてそろえてください。初期の費用が安くても、毎月の費用や連携の費用が高い製品はよくあります。

5年間の費用 = 初期の費用 + (毎月の費用 × 60か月) + 連携・追加機能の費用 + 社内の手間(導入時の作業時間 × 人件費)

この5年間の費用と、手順3で出した年間の削減コストの5年分を比べると、投資として見合うかどうかが分かります。

# AIで時間を減らす

  • 施策カードの下書き:根っこの原因とあるべき姿を渡し、「施策カードの項目(名前・解消する根っこ・効果・費用・期間・前提・関係部門・リスク)で、施策を洗い出して」と頼みます。
  • 前後の関係の確認:施策の一覧を渡し、「先に終わっていないと進められない施策の組み合わせを挙げて」と頼むと、順番の見落としに気づけます。
  • 注意:費用の数字は、AIに推測させず、業者の見積もりや契約の数字を使います。

# つまずきやすい所

  • 全部を同時に始める:担当者も現場も、同時にいくつもの変化には耐えられません。同時に進める施策は、2つ程度までにします。
  • 前後の関係を無視する:持ち主が決まる前につなぎ込むと、つないだ後で作り直しになります。
  • 製品を先に決めてしまう:この段階で1つに決めると、業務を聞いた後で合わないと分かっても、引き返せなくなります。

# 手順7. 経営層で合意を取る

# 実際にあった話：意見が割れたときは、比べられる数字を出す

ある会社で、部門をまたいで使う業務のシステムを入れ替えるとき、2つの部門の責任者の意見が割れました。一方はクラウド型を、もう一方は特定のメーカーの製品を推していました。どちらにも理由があり、話し合いは平行線でした。

そこで、両方の候補について、条件をそろえて見積もりを取り、価格の交渉もしたうえで、金額の差をはっきり示しました。比べられる数字が出たことで、話が「どちらが好きか」から「どちらが組織に得か」に変わり、合意がまとまりました。

このとき作った業者との関係は、グループの別の会社で同じ入れ替えをしたときにも生きました。条件を伝えるとすぐに、最初から低い価格で提案が出てきたのです。

# うまくいかなかった話：提案が通らなかったとき

別の会社では、指定された製品が、ほかのシステムとのつながりの面で運用に合わないと判断し、代わりの案を出しました。しかし、経営の判断で見送られました。

その後は、決まった製品のまま、手作業を前提にした運用の流れを作り、拠点の間の調整と、改善のための定例の会議を新しく設けて、運用を安定させました。

振り返ると、代わりの案を出す前に、経営層が何を一番大事にしているか(費用なのか、時期なのか、関係なのか)をもっと聞いておくべきでした。①で書いた「3つの層の考え方の違い」のように、経営層と現場では、見ているものが違うのです。

# 何をするか

手順3の数字と手順6の計画を持って、経営層に投資の判断をしてもらいます。あわせて、部門の責任者、現場、長く業務を支えてきたベテランの方へ説明し、協力を得ます。

# 経営層向けの資料の構成

経営層向けの資料は、次の順で作ります。枚数は、本編で5〜6枚程度に収めます。

  1. 結論:何に、いくら使って、何が良くなるのか(1枚)
  2. 今の姿:手順2のデータの流れ図と、手作業の場所(1枚)
  3. 困りごとの大きさ:手順3の年間コストと、属人化のリスク(1枚)
  4. あるべき姿:手順5の全体図(1枚)
  5. 計画と費用:手順6の段階的な計画と、5年間の費用、削減の見込み(1枚)
  6. お願いしたいこと:判断してほしいこと、協力してほしいこと(1枚)

結論を最初に置くのが大事です。経営層は、最初の1枚で「聞く価値があるか」を判断します。

# 説明で気をつけること

  • 数字は、根拠と一緒に示す:「年間〇〇時間」と言ったら、「〇日間計った平均です」と添えます。根拠のない数字は、一度疑われると、ほかの数字も信じてもらえなくなります。
  • 良いことだけを言わない:現場の負担が一時的に増えること、うまくいかない可能性があることも伝えます。後から分かるより、先に言っておくほうが信頼されます。
  • 選択肢を示す:「この案しかない」ではなく、「A案・B案・何もしない場合」を並べます。何もしない場合のコストも示すと、判断しやすくなります。

# よく聞かれる質問と、答え方

  • 本当にそんなに減るのか(答え方の例:計った方法と日数を説明する。控えめに見た場合の数字も示す)
  • 今のままでは駄目なのか(答え方の例:何もしない場合の5年間のコストと、属人化のリスクを示す)
  • もっと安い方法はないのか(答え方の例:比べた候補と、選ばなかった理由を示す)
  • 失敗したらどうなるのか(答え方の例:最初の施策は小さく、元に戻せるものにしてあると説明する)
  • 現場は納得しているのか(答え方の例:聞き取りの結果と、責任者の意見を示す)

# トップから話してもらう

経営層で合意が取れたら、トップから各部門の責任者へ、改めて伝えてもらいます。手順1の呼びかけに加えて、今度は「この計画で進める」ことを伝えてもらいます。

トップの言葉があると、各部門の責任者も「上が決めたことだから」と動きやすくなります。担当者が直接お願いするより、ずっと話が早く進みます。

それでも進まない部門があれば、人事や関係部署を巻き込みます。例えば、業務の分担や役割の変更が絡む場合は、人事の担当者に同席してもらうと、話が整理されやすくなります。

# 長く業務を支えてきたベテランの方への説明

ここが、合意の中で一番時間がかかり、一番大事なところです。

長く業務を支えてきたベテランの方は、今のやり方を作ってきた本人であることが多いです。改善の話は、その人にとって「自分のやり方を否定される話」に聞こえやすいのです。

説明の進め方です。

  1. まず、これまでの貢献を認める:「今の業務が回っているのは、〇〇さんが工夫してこられたからです」
  2. 個別に、丁寧に話す:会議の場ではなく、1対1で時間を取る
  3. 負担が増えることも、隠さず伝える:手順が増える、覚えることが増える、など
  4. 全体にとっての意味を共有する:「会社全体で残業が月〇〇時間減ります」「〇〇さんが休んでも業務が止まらなくなります」
  5. 判断の材料として渡す:「どう思われますか」と意見を聞く
  6. できれば、チームに入ってもらう:業務を一番知っている人として、役割を持ってもらう

声のかけ方の例です。

〇〇さんが長年工夫してこられたおかげで、今の業務が回っていることはよく分かっています。今回の見直しで、〇〇さんの手順が一部増えてしまうところがあります。そのかわり、会社全体では月の残業が〇〇時間ほど減る見込みです。業務を一番よくご存じなのは〇〇さんなので、ぜひ一緒に進めていただけないでしょうか。

最後の「一緒に進めていただけないでしょうか」が大事です。反対する側から、一緒に進める側に移ってもらえると、現場への説明が一気に進みます。ベテランの方が「これなら大丈夫」と言えば、ほかの人も安心するからです。

# 反対のタイプと、向き合い方

反対には、いくつかのタイプがあります。タイプによって、向き合い方が変わります。

  • 不安:「新しいものは覚えられない」→ 教える時間と、困ったときの窓口を約束する
  • 損をする:「私の仕事が増えるだけ」→ 負担を認め、減る作業も具体的に示す。全体の意味を共有する
  • 面倒:「今のままで困っていない」→ 手順3の数字と、属人化のリスクを示す
  • 立場:「聞いていない」→ 事前に個別に話す。決める前に意見を聞く

4つ目の「聞いていない」は、内容ではなく、順番の問題です。影響を受ける人には、全体に発表する前に、個別に話しておくだけで、多くの反対は防げます。

# AIで時間を減らす

  • 資料の構成案:目的・数字・計画を渡し、「経営層向けに、結論から始まる6枚の構成にして」と頼みます。
  • 想定問答:「この計画に対して、経営層・部門の責任者・現場がそれぞれ言いそうな反対意見と、答え方を出して」と頼むと、準備の抜けが減ります。
  • 注意:個人を特定できる話や、社内の人間関係はAIに入れないでください。

# つまずきやすい所

  • 資料が分厚い:経営層は、細かい説明より結論を求めています。詳細は別の資料にまとめ、聞かれたら出します。
  • 反対する人を説得しようとする:説得しようとすると、相手は身構えます。まず話を聞き、相手の心配をはっきりさせてから、それに答えます。
  • 合意を一度で済ませようとする:経営層、責任者、現場、ベテランの方と、相手ごとに説明の仕方を変えます。同じ資料を全員に見せるだけでは、伝わりません。

直して守る(手順8〜10)

# 手順8. 施策ごとに実行する

# 実際にあった話：教える順番と、外への説明

ある会社で受発注のシステムを入れ替えたとき、使い方の説明は、管理者 → 現場のリーダー → 全社員の順に段階を分けて行いました。先に管理者とリーダーが使えるようになっていたので、全社員への説明の後は、現場の中で質問が解決するようになりました。

別の会社では、お客様に郵送していた毎月の請求書を、専用のアプリでの電子配信に切り替えました。このときは、システムの設定よりも、お客様向けの案内文と、拠点向けの説明資料づくりに力を入れました。外の人に影響する変更は、説明の準備が成否を分けます。

データの移し替えで苦労したこともあります。古いシステムの過去の記録が、新しいシステムにそのままでは引き継げないと分かったのです。記録の情報を取り出して、読める形のファイルに変えて残す仕組みを自分で作り、過去の記録を守りました。移し替えでは、「何が引き継げないか」を最初に確かめるのが大事です。

# 何をするか

計画した施策を、1つずつ実行します。ここからは、通常のシステム導入の流れに近くなります。ただし、手順1〜7で作った設計図と原則に沿って進める点が、これまでの「個別の導入」と違います。

施策ごとに、次の流れで進めます。

  1. チームを立ち上げる
  2. 業務を詳しく聞く(複数回)
  3. 業務フローと要件をまとめる
  4. 製品を最終決定し、契約する
  5. テストと移行の準備をする
  6. 導入し、立ち上がりを支える

# 1. チームを立ち上げる

施策ごとに、小さなプロジェクトのチームを作ります。

チームの役割

  • 責任者(誰が:経営層の1人、やること:最終の判断。部門をまたぐ問題の解決)
  • 推進役(誰が:担当者(この有料部分を読んでいる方)、やること:計画、進み具合の管理、関係者の調整)
  • 部門の代表(誰が:各部門から1人、やること:業務の説明、現場への伝達、テスト)
  • 業務に詳しい人(誰が:ベテランの方など、やること:例外の処理や細かい手順の確認)
  • 業者(誰が:導入する業者、やること:設定、データの移し替え、教育の支援)

プロジェクトの約束ごとを1枚にする

チームを立ち上げたら、最初に次の項目を1枚にまとめ、全員で確認します。

  • この施策の目的と、成功の物差し(手順1・3から)
  • 範囲(何をやるか、何をやらないか)
  • 期間と、大きな節目の日
  • チームの役割と連絡の方法
  • 定例の打ち合わせ(例：毎週30分)
  • 困ったときに、誰が判断するか

特に「何をやらないか」を書いておくことが大事です。進めるうちに、「ついでにこれも」という要望が必ず出てきます。範囲を決めておかないと、際限なく広がり、終わらなくなります。

近い未来を見せる

チームの最初の打ち合わせでは、「導入後、仕事がこう変わる」という姿を具体的に見せます。

  • 手順5の「あるべき姿」の図
  • 1日の仕事の流れが、どう変わるか(朝の作業、月末の作業など)
  • 減る作業と、新しく増える作業

抽象的な「効率化」ではなく、「月末の突き合わせがなくなり、定時で帰れる」のような具体的な姿を示すと、チームの気持ちがそろいます。

# 2. 業務を詳しく聞く(複数回)

手順2の聞き取りより、もう一段詳しく聞きます。聞くときは、③の「ヒアリングの漏れを防ぐチェックシート」を手元に置くと、漏れが大きく減ります。1回では、例外の処理や暗黙の手順は出てきません。最低でも3回に分けます。

  • 1回目(目的:全体の流れ、聞くこと:通常の処理を、最初から最後まで)
  • 2回目(目的:例外、聞くこと:普段と違う処理。月末・年度末、間違えたとき、急ぎのとき)
  • 3回目(目的:確認、聞くこと:1・2回目をまとめたものを見せ、抜けや誤りを直してもらう)

例外を聞き出す質問

2回目では、次の質問で例外を聞き出します。

  • 年に数回しかやらない処理はありますか
  • 途中で取り消したり、やり直したりするのは、どんなときですか
  • 急ぎで処理するのは、どんなときですか。そのとき、手順は変わりますか
  • 新しい人に教えるとき、一番間違えやすいところはどこですか
  • 「本当はこうしたいけど、今はできない」ことはありますか

最後の質問からは、あるべき姿への改善の種が出てくることがあります。

毎回、まとめて見せる

聞いた内容は、毎回まとめて相手に見せます。話した内容と、理解した内容がずれていることはよくあります。早めに直しておかないと、システムができてから「こんなはずじゃなかった」になります。

# 3. 業務フローと要件をまとめる

業務フローを2つ作る

今の業務フローと、導入後の業務フローを作ります。誰が、どの順番で、何をするかを、部門ごとに横に並べた図にすると分かりやすくなります。

2つを並べると、次のことがはっきりします。

  • なくなる作業
  • 担当が変わる作業
  • 新しく増える作業

「新しく増える作業」は、必ず該当する部門の責任者に確認します。ここを確認しないまま進めると、導入後に「聞いていない」という反発が出ます。

要件を3段階に分ける

業者に伝える要件(システムに求めること)は、3段階に分けます。

  • 必須(意味:これがないと業務が回らない、例:社員の情報を、人事のシステムから自動で受け取れる)
  • あると良い(意味:あれば楽になるが、なくても回る、例:スマートフォンから勤務の申請ができる)
  • 今回は見送り(意味:将来は欲しいが、今回は求めない、例:グループ会社との勤務の共有)

段階を分けておくと、費用を抑えたいときに、何を削れるかがすぐ分かります。全部を「必須」にすると、費用が膨らみ、比べることもできなくなります。

業者への依頼書に書く項目

製品を比べるときは、業者に依頼書を渡して、提案と見積もりをもらいます。依頼書には、次の項目を書きます。

  • 組織の概要(規模、部門、拠点)
  • この施策の目的と、成功の物差し
  • 今の業務フローと、導入後の業務フロー
  • 要件(必須・あると良い・見送り)
  • つなぐ必要のあるシステムと、渡すデータ
  • 守るべき制約(セキュリティ、制度、契約)
  • 希望する期間と、大きな節目
  • 提案に含めてほしいもの(費用の内訳、5年間の費用、体制、導入の手順、サポート)

依頼書を渡すと、業者ごとの提案を同じ物差しで比べられます。業者がどこを見て見積もるか、どう書けば見積もりが下がりやすいかは、③で詳しく書きます。第2回で書いた「部門ごとの要望に、部門ごとの最適な答えが返ってくる」状態を防ぐことにもなります。

# 4. 製品を最終決定し、契約する

業者の提案を、手順6の比べる観点で評価します。見積もりの読み方は、③を参考にしてください。可能なら、実際の画面を、現場の担当者に触ってもらいます。担当者が「これなら使える」と言うかどうかは、とても大事な判断材料です。

契約の前に確かめること

  • データの取り出し:やめるときに、データをどんな形式で、いくらで取り出せるか
  • 連携の費用:ほかのシステムとつなぐ費用は、見積もりに含まれているか。相手のシステムの側にも費用がかかるか
  • 保守の期間:いつまで保守が続くか。終わるときは、どれくらい前に知らせてもらえるか
  • 費用の上がり方:使う人数が増えたとき、年数がたったときに、費用がどう変わるか
  • 責任の分担:障害が起きたとき、どこまでが業者の責任か

最初の「データの取り出し」は、特に大事です。ここを確かめずに契約すると、将来、乗り換えたくても乗り換えられなくなります。

# 5. テストと移行の準備をする

現場の1日の流れでテストする

テストは、機能を1つずつ確かめるだけでは足りません。現場の担当者が、実際の1日の流れに沿って操作するテストを必ず行います。

例えば、受発注のシステムなら、次のような流れでテストします。

  1. 取引先から注文が届き、受注を登録する
  2. 在庫を引き当てる(足りないときの扱いも)
  3. 倉庫に出荷を指示する
  4. 出荷の実績を入れる
  5. 請求書を作り、会計のシステムに売上が正しく渡る
  6. 出荷の前に、注文が変更・取り消しされた場合の扱いを確かめる

最後の「注文の変更・取り消し」のような例外こそ、手順8の2で聞き出したものを使って、必ずテストします。

データの移し替えの準備

古いシステムから新しいシステムへデータを移すときは、先にデータの整理が必要です。

  • 重複している登録を1つにまとめる(同じ人が2人登録されている、など)
  • 使っていない登録を消す(退職した人、終わった取引先など)
  • 表記をそろえる(全角と半角、部署名の書き方など)

この整理は、思った以上に時間がかかります。古いデータほど、ばらつきがあるからです。移し替えの予定日から逆算して、早めに始めます。

並行して動かすか決める

お金に関わるシステムなど、間違いが許されないものは、しばらく新旧の両方を動かし、結果が一致するかを確かめることがあります。負担は大きいですが、安心して切り替えられます。

並行して動かすかどうかは、間違えたときの影響の大きさで決めます。影響が小さければ、並行させずに切り替え、問題があれば直す方法でも構いません。

# 6. 導入し、立ち上がりを支える

使い方の説明

使い方の説明は、全員を集めた説明会だけでは足りません。次の3つを組み合わせます。

  • 説明会:全体の流れと、変わる点を説明する
  • 手順の資料:画面の写真入りで、よく使う操作だけをまとめる(1業務1枚)
  • 身近な相談役:各部門に1人、先に覚えてもらい、周りの人の質問に答えてもらう

3つ目の相談役は、チームの「部門の代表」が適任です。同じ部門の人に聞けるほうが、気軽に質問できます。

立ち上がり後の1か月

導入後の1か月は、問い合わせが集中します。この期間は、次のことを決めておきます。

  • 問い合わせの窓口(誰に、どうやって聞くか)
  • よくある質問のまとめ(毎週更新する)
  • チームの短い打ち合わせ(最初の2週間は毎日10分など)
  • 業者への問い合わせの方法と、対応の時間

最初の1か月で「使いにくい」「前のほうが良かった」という声が出るのは、ごく普通のことです。ここで一つ一つの声に丁寧に答えると、2か月目からは急に落ち着きます。

# AIで時間を減らす

  • 聞き取りの抜けの確認:業務フローを渡し、③の「ヒアリングの漏れを防ぐチェックシート」の観点で、「聞けていない例外や時期はどれか」と聞きます。
  • テストの筋書き:導入後の業務フローを渡し、「現場の1日の流れに沿ったテストの手順を作って。例外の場面も入れて」と頼みます。
  • 手順の資料・よくある質問:画面の操作の説明を渡し、「1業務1枚の手順書」と「よくある質問」の下書きを作ってもらいます。
  • 注意:テストのデータには、本物の個人の情報を使わず、架空のデータを用意します。

# つまずきやすい所

  • 範囲が広がり続ける:「ついでに」の要望は、記録して次の施策に回します。今の施策の範囲は守ります。
  • テストを業者任せにする:業者のテストは、機能が動くかの確認です。業務が回るかの確認は、組織の側でしかできません。
  • 古いシステムを残し続ける:新旧の両方を使える状態が続くと、現場は慣れた古いほうを使い続けます。切り替えの日を決めたら、古いほうは見るだけにするなど、はっきり区切ります。

# 手順9. 効果を確かめる

# 実際にあった話：数字と一緒に、現場の一言を

請求書を電子配信に切り替えた会社では、効果を報告するときに、封入や宛先の二重確認にかかっていた手間がなくなったことを数字で示しました。あわせて、拠点の担当者の「月初めの封入作業がなくなって、本当に楽になった」という一言も添えました。

経営層が一番反応したのは、数字よりも、その一言でした。数字は判断の根拠になり、現場の声は次の施策への後押しになります。 両方をそろえて報告するのがおすすめです。

# 何をするか

施策が落ち着いたら、手順3で計った数字と比べて、実際にどれだけ変わったかを確かめます。結果を経営層とチームに報告し、次の施策に進みます。

# 同じ方法で計る

効果を確かめるときは、手順3と同じ方法で計ることが大事です。聞き取りで出した数字なら聞き取りで、横で見て計った数字なら同じように計ります。方法が違うと、比べられません。

計る時期は、導入の直後ではなく、慣れてからにします。

  • 1か月後:大きな問題がないかの確認
  • 3か月後:効果の確認(慣れて安定したころ)

導入の直後は、慣れていないため、むしろ時間がかかることがあります。そこで計ると、「効果がない」と誤った判断をしてしまいます。

# 報告の型

報告は、次の型でまとめます。

  • 目的(内容:手順1で決めた目的の1文)
  • 物差しの変化(内容:導入前と導入後の数字を並べる(作業時間、やり直し、属人化した作業の数))
  • 費用(内容:実際にかかった費用(予定との差も))
  • 良かったこと(内容:現場の声も添える)
  • 残った課題(内容:うまくいかなかったこと、まだ残っている手作業)
  • 次の施策(内容:計画の見直しと、次に進める施策)

現場の声は、短くても入れてください。「月末に定時で帰れるようになった」という一言は、数字と同じくらい経営層に響きます。

導入前の数字があるから、効果を示せるのです。手順3を丁寧に行う理由は、ここにもあります。

# 効果が出なかったときは

効果が思ったほど出ないこともあります。そのときは、次の3つを確かめます。

  • 使われていない:確かめ方は、実際の利用の記録を見る。現場に聞く。対処は、使いにくい点を直す。説明をやり直す
  • 古い手順が残っている:確かめ方は、業務フローどおりに動いているか、横で見る。対処は、古い手順をやめることを、責任者から改めて伝える
  • 見込みが甘かった:確かめ方は、手順3の数字の取り方を見直す。対処は、計画の数字を直し、次の施策の見積もりに生かす

2つ目の「古い手順が残っている」は、とてもよくあります。新しいシステムで自動になったのに、念のため手で確かめる作業が残っている、などです。「もうやらなくていい」と、はっきり伝えることが必要です。

# AIで時間を減らす

  • 報告書の下書き:導入前と導入後の数字、費用、現場の声を渡し、「報告の型(目的・物差しの変化・費用・良かったこと・残った課題・次の施策)で1枚にまとめて」と頼みます。
  • 効果が出ない原因の洗い出し:状況を渡し、「使われていない・古い手順が残っている・見込みが甘い、のどれに当たりそうか、確かめる方法も」と聞きます。

# つまずきやすい所

  • 計るのを忘れる:導入が終わると、ほっとして効果の確認を忘れがちです。計る日を、手順8の計画に最初から入れておきます。
  • 良い数字だけを報告する:残った課題も正直に報告すると、次の施策への信頼につながります。

# 手順10. 元に戻らない仕組みを作る

# 実際にあった話：問い合わせの流れを決めておく

ある会社で、全社に新しい仕事の道具を広げる準備をしたとき、各拠点に「拠点の相談役」を置く仕組みを設計しました。社員 → 拠点の相談役 → 情報システムの担当 → 業者、と段階を踏んで問い合わせが上がる流れです。

あわせて、急ぎかどうかを見分ける基準、問い合わせを記録する表、どこまでを誰が対応するかの線引き、よく使う言葉の用語集も作りました。問い合わせが特定の人に集中しないようにするのが狙いです。

仕組みの中に人の役割を組み込んでおくと、担当者が替わっても、同じ流れで回り続けます。元に戻らないための決まりは、システムの決まりだけでなく、人の流れの決まりでもあるのです。

# 何をするか

直した後に、各部門がまた個別にシステムを入れれば、数年で第1回の「拡大期・干渉期」に戻ります。そうならないための決まりと、続けるための体制を作ります。

この手順が、「1つずつ直す」と「紐解く」の違いを決める、一番大事な手順です。

# 新しく入れるときの確認ルール

新しいシステムを入れるとき、または今のシステムを入れ替えるときは、次の項目を確かめてから決める、というルールを作ります。

導入前の確認項目

  1. 目的は何か。どの業務の、どんな困りごとを解決するか
  2. 同じことが、今あるシステムでできないか
  3. 扱うデータは何か。そのデータの持ち主は、どのシステムか
  4. 同じ情報を、2か所以上で入力することにならないか
  5. ほかのシステムと、どうつなぐか。その費用はいくらか
  6. やめるときに、データを取り出せるか
  7. 5年間の費用はいくらか
  8. 社内の担当者は誰か。その人がいなくなったら、誰が引き継ぐか
  9. セキュリティの制約(データの置き場所、アクセスの管理)を守れるか
  10. システム台帳に登録したか

この10項目を1枚の用紙にし、新しく入れるときは必ず記入して、推進役(または情報システムの担当)に提出する決まりにします。

小さなツールや、無料のサービスも対象にします。「無料だから」「部門だけで使うから」という理由で入れたものが、数年後に大事なデータを抱え込んでいる、ということはよくあるからです。

# システム台帳を更新し続ける

手順2で作ったシステム台帳は、作って終わりではありません。更新し続けて、初めて意味があります。

  • 更新する担当者を決める:1人に決め、代わりの人も決めておく
  • 更新するタイミングを決める:新しく入れたとき、やめたとき、契約を更新したとき、担当者が変わったとき
  • データの流れ図も一緒に直す:台帳と流れ図は、セットで更新する

# 年に1回、全体を見直す

年に1回、全体を見直す場を設けます。経営層、推進役、各部門の代表が集まり、次のことを確かめます。

  • システム台帳とデータの流れ図に、変わったところはあるか
  • 手作業(点線の矢印)は増えていないか
  • 契約の更新や保守の終了が近いものはないか
  • 新しく入れたものは、確認ルールを通っているか
  • 段階的な計画の、次の施策は何か

年度の予算を決める前の時期に行うと、次の年の費用の計画にそのまま生かせます。

# 情報システムの担当がいない組織では

小さな組織では、専任の担当者を置くのは難しいかもしれません。その場合は、次の方法があります。

  • 兼務の担当者を決め、時間を確保する:例えば、毎月の何時間かを、この仕事のための時間として決める。「手が空いたらやる」では、必ず後回しになります
  • 外部の相談役を持つ:特定の業者ではなく、組織の側に立って助言してくれる人を、定期的に頼む
  • 確認ルールだけは必ず守る:担当者がいなくても、新しく入れるときの確認用紙だけは、必ず経営層が確かめてから決める

第1回で書いた、全体を見る軸がなくなる原因の1つ目は「全体を見る人がいない」でした。専任でなくても、「全体を見る役割」を誰かに持たせることが、元に戻らないための一番の対策です。

# AIで時間を減らす

  • 確認用紙の作成:この章の10項目を渡し、「記入しやすい1枚の用紙にして。記入例も」と頼みます。
  • 台帳の差分の確認:去年と今年のシステム台帳を渡し、「増えたもの・減ったもの・契約の更新が近いもの」を挙げてもらうと、年1回の見直しの準備が早くなります。

# つまずきやすい所

  • ルールが厳しすぎる:確認の手続きが重すぎると、現場は隠れてツールを使い始めます。小さなものは簡単に、大きなものは慎重に、と手続きの重さに差をつけます。
  • 見直しの場が形だけになる:年1回の見直しで、毎回「変わりなし」で終わるようなら、台帳の更新が止まっているサインです。

通しの事例：架空の会社の場合

ここまでの10の手順を、架空の会社を例に通して見てみます。手順ごとの「実際にあった話」は一場面ずつなので、ここでは1つの組織で最初から最後まで通すとどうなるかを示します。登場する組織と数字は、すべて架空のものです。

# 会社の状況

  • 社員は約100人の卸売の会社。受注と出荷を担当する部門は8人
  • 販売管理のシステムのほかに、倉庫の在庫はExcel、会計は別のシステムで、ばらばらに動いている
  • 注文はFAXとメールで届き、繁忙期には出荷が遅れる
  • 倉庫の在庫の数を正確に分かっているのは、長く勤めるベテランの社員1人だけ

# 手順1〜4:知る

経営層と話し、一番大事な目的を「受注の部門の繁忙期の残業を半分にし、ベテラン社員が休んでも在庫の数が分かるようにする」と決めました。社長から全体へ、見直しを始めることと、協力のお願いを伝えてもらいました。

聞き取りとデータの流れ図から、点線の矢印(手作業)が、販売管理・倉庫のExcel・会計の間に集中していることが分かりました。

主な手作業を計ると、次のようになりました。

  • FAXとメールの注文を販売管理に打ち直す(年間の時間:約120時間)
  • 出荷の後に、請求書を手で作り直す(年間の時間:約60時間)
  • 倉庫のExcelと販売管理の在庫を突き合わせる(年間の時間:約50時間)
  • 新しい取引先・商品を3か所に登録する(年間の時間:約30時間)
  • 合計(年間の時間:約260時間)

課題をカードにしてまとめると、4つのうち3つが「商品と取引先の情報が3か所にある」という根っこに、残りの1つが「注文がシステムの外で届く」という根っこにつながっていました。

# 手順5〜7:描く

原則として「入力は1回だけ」「正しいデータは1か所」を決めました。商品と取引先の情報の持ち主を「販売管理のシステム」とし、倉庫と会計はそこから受け取る形を、あるべき姿として描きました。

施策を次の順に並べました。

  1. 商品と取引先の情報を整理し、販売管理のシステムに一本化する(第1段階)
  2. 倉庫の在庫を、販売管理のシステムとつなぐ。請求書も販売管理から出す(第2段階)
  3. 主な取引先からの注文を、Webの受注画面で受ける(第2〜3段階)

経営層には、「年間約260時間の手作業と、ベテラン社員1人に頼る在庫の管理を、5年間で〇〇万円の投資でなくす」という結論から説明しました。何もしない場合の5年間のコストと、ベテラン社員が長く休んだ場合に在庫の数が分からなくなるリスクも示しました。

倉庫のベテラン社員には、事前に1対1で話しました。これまでの工夫を認めたうえで、一時的に入力の作業が増えることを伝え、チームに「業務に詳しい人」として入ってもらいました。その社員が「この形なら、私が休んでも出荷が止まらない」と話してくれたことで、倉庫のほかの社員も前向きになりました。

# 手順8〜10:直して守る

第1段階では、商品の情報の整理に、思ったより時間がかかりました。売っていない商品の登録が残っていたり、同じ商品が別のコードで登録されていたりしたためです。

第2段階でつなぎ込みを終え、3か月後に計り直すと、4つの手作業は合計で年間約90時間まで減っていました。残ったのは、Webの受注に切り替えていない一部の取引先のFAXの注文です。これは次の段階の課題として、計画に残しました。

最後に、新しいシステムを入れるときの確認用紙を作り、管理部長が確かめてから決める決まりにしました。年度の予算の前に、年1回の見直しの場も設けました。

よくある失敗10

最後に、筆者がよく見てきた失敗をまとめます。始める前と、途中で迷ったときに見返してください。

  1. 目的が「新しいシステムを入れること」になっている:手段が目的になると、入れた時点で終わってしまう
  2. 数字を取らずに始める:優先順位も合意も効果の確認も、感覚頼みになる
  3. 困りごとだけを集める:原因が見えず、1つずつ直すことになる
  4. 製品を先に決める:業務に合わなくても、引き返せなくなる
  5. 全部を同時に始める:担当者も現場も疲れ切り、どれも中途半端になる
  6. 影響を受ける人に、後から伝える:内容ではなく、順番で反対される
  7. ベテランの方を説得しようとする:説得ではなく、話を聞き、一緒に進める側に入ってもらう
  8. テストを業者に任せる:業務が回るかは、組織の側でしか確かめられない
  9. 効果を計らない:次の施策への説得材料がなくなる
  10. 直して終わりにする:確認ルールと台帳がなければ、数年で元に戻る
